# 企业级 RAG 知识中台 PRD

| 项 | 内容 |
|---|---|
| 文档版本 | v1.0 |
| 产品形态 | Web 管理后台（知识治理）+ 本地连接层（对接 RAG 引擎） |
| RAG 引擎 | FastGPT（云服务），可替换为 Dify 或自研 |
| 知识规模 | 20 份文档 / 7 类知识 / 20 条评测用例 |

> 本文档描述产品层面的设计取舍，不绑定具体引擎实现。所有企业名、型号、政策条款均为虚构示例。

## 0. 一页式架构

```
┌──────────────────────────────────────────────────────────────┐
│ L3 应用交付层   智能客服 · 员工助手 · 服务商助手（不在本期范围）    │
└───────────────────────────▲──────────────────────────────────┘
                            │ 问答 API
┌───────────────────────────┴──────────────────────────────────┐
│ L2 RAG 能力层   FastGPT：解析 · 切片 · 向量化 · 检索 · 重排 · 生成   │
└───────────────────────────▲──────────────────────────────────┘
                            │ 4 个概念接口
┌───────────────────────────┴──────────────────────────────────┐
│ L1 知识治理层   本产品：知识库 · 版本 · 审核 · 权限 · 评测 · 发布     │
│                13 个模块 · 7 段流程 · 3 道门槛                  │
└──────────────────────────────────────────────────────────────┘
```

**一句话结论**：平台不解决「模型答得好不好」，解决「知识能不能用、谁能用、效果如何验证」。

## 1. 项目概述

### 1.1 背景与问题

企业售后知识分散在商品中台、共享盘、客服系统和渠道运营手里，客服回答一个问题要跨四个系统。由此产生四类问题：

1. **口径不一致**：同一政策存在两个版本同时在用，天猫与自营客服说法不同。
2. **过期知识难下线**：政策修订后旧版本仍被检索到，出现过按旧政策承诺退换的纠纷。
3. **修订无留痕**：谁改的、依据是什么、有没有人审过，查不到。
4. **AI 不敢用**：直接把文档丢给大模型，答错了没人能追溯是哪条知识出的问题。

### 1.2 产品定位

> 面向知识运营、业务审核人与 AI 产品经理的知识治理平台，位于 RAG 能力引擎之上；管理知识从录入到上线的全生命周期，让每一条上线知识可审核、可回溯、可评测。

| 层级 | 系统 | 负责 | 不负责 |
|---|---|---|---|
| 知识治理层 | 本产品 | 知识库、版本、审核、权限、任务、验收、评测、发布、审计 | 解析算法、向量检索、模型生成 |
| RAG 能力层 | FastGPT | 解析、切片、Embedding、检索、重排、生成 | 业务口径、审核规则、版本治理 |
| 应用交付层 | 客服/助手 | 面向最终用户提供问答 | 知识管理与评测 |

### 1.3 新手术语速查

| 术语 | 新手的理解 |
|---|---|
| RAG | 先查企业知识，再让模型依据查到的内容回答 |
| 切片（Chunk） | 把长文档拆成便于检索的小段 |
| Embedding | 把文字转成可以计算相似度的向量 |
| 召回 | 根据问题找出可能相关的片段 |
| Top K | 返回的前 K 条候选 |
| 重排（Rerank） | 对候选再排序，让更相关的排前面 |
| 兜底 | 没查到知识时明确说不知道，而不是编造 |

### 1.4 目标与边界

| 类别 | 内容 |
|---|---|
| 业务目标 | 让知识从「散落文件」变成「可审核、可发布、可检索、可评测」的企业资产 |
| 体验目标 | 运营人员不理解向量技术，也能完成上传、审核、发布和效果检查 |
| 质量目标 | 回答可追溯到有效知识来源；无知识时明确兜底，不编造政策 |
| 本期边界 | 不自研文档解析器、Embedding 模型、向量数据库、Rerank 模型与模型网关 |

### 1.5 交付阶段

| 阶段 | 周期 | 产出 |
|---|---|---|
| 方案 | 1–2 周 | PRD、13 模块原型、角色权限、接口清单、评测方案 |
| 引擎验证 | 2–3 天 | 20 份文档入库、检索与问答跑通 |
| 真实集成 | 2–4 周 | 连接层、状态回写、发布同步 |
| 试点 | 2 周 | 售后知识库全量 + 智能客服灰度 |

## 2. 产品范围与系统边界

### 2.1 角色与权限

**原则**：内容正确性、处理质量、最终回答质量与生产发布，由不同角色负责，避免同一个人既提交、又审核、又放行。

| 角色 | 一句话职责 | 不能做什么 |
|---|---|---|
| 知识运营 | 维护知识、验收处理结果、做检索调试 | 不能审核自己提交的 P0 知识 |
| 业务审核人 | 确认事实、适用范围与高风险口径 | 不能改检索参数、不能直接发布 |
| AI 产品经理 | 组织评测、登记对话验证、提交发布审批 | 不能绕过审核直接入库 |
| 客服业务人员 | 在真实场景中验证并反馈问题 | 不能修改知识内容 |
| 系统管理员 | 维护成员、连接与审计 | 不能绕过审核与评测门槛发布 |

**三条硬约束**

1. 提交人 ≠ 业务审核人；P0 知识（安全、隐私、退款）强制双人。
2. 系统管理员不能绕过业务审核与评测直接发布。
3. 生产发布必须走线下审批，平台只做门槛与留痕。

### 2.2 功能模块

| 编号 | 优先级 | 模块 | 核心内容 | 关键操作 |
|---|---|---|---|---|
| F-01 | P0 | 知识库管理 | 名称、业务域、负责人、可见范围、测试/生产 RAG 资源状态 | 新建、编辑、归档 |
| F-02 | P0 | 文档与版本 | 原文、分类、标签、版本、有效期、审核记录、RAG 环境 | 上传、存草稿、提交审核、建新版本 |
| F-03 | P0 | 数据源同步 | CMS / 在线文档 / 工单副本的增量同步与失败重试 | 新建、立即同步、重试 |
| F-04 | P0 | 业务审核 | 新旧版本对比，核对事实、范围、有效期、高风险口径 | 三项确认后通过、填写原因驳回 |
| F-05 | P0 | 入库任务 | jobId、文档版本、环境、步骤、进度、状态、RAG 资源 ID | 推送 API、查看、重试 |
| F-06 | P0 | 处理结果验收 | 解析摘要、切片列表、原文定位、数量校验、异常项 | 验收通过、退回重处理 |
| F-07 | P0 | 检索调试 | 检索配置、Top K、相关度、来源、预期切片、诊断结论 | 运行检索、标记问题、确认通过 |
| F-08 | P0 | 批量评测与发布 | 5 / 40 / 200 三阶段、指标、失败样本、发布状态 | 运行阶段、阻断发布、生产发布 |
| F-09 | P0 | 问题案例 | 来源类型、问题摘要、时间、只读证据快照 | 查看证据、标记已处理 |
| F-10 | P0 | 权限与审计 | 角色、知识库数据权限、API 密钥、关键操作日志 | 授权、撤权、导出审计 |
| F-11 | P1 | 运营总览 | 已发布知识、待处理、通过率、P0 风险、流程指引 | 跳转各模块 |
| F-12 | P1 | 运营统计 | 文档数、发布成功率、阶段通过率、失败类型、高频问题 | 筛选、导出 |
| F-13 | P1 | RAG 引擎配置 | Provider、服务地址、密钥托管、dataset 映射、模型参数 | 测试连接、保存配置 |

### 2.3 三方职责边界

| 系统 | 主要职责 | 为什么不能合并 |
|---|---|---|
| 本产品（治理） | 管知识是否可用、谁批准、何时上线 | 审核与发布是业务判断，引擎不承担 |
| FastGPT（能力） | 把文档处理成可检索的索引，并生成回答 | 算法迭代快，不应绑定业务规则 |
| 问答应用（交付） | 面向最终用户提供问答体验 | 渠道与形态多变，不应改动治理逻辑 |

**为什么审核通过后不能直接上线**：文档内容正确，不代表 AI 能正确解析、切片、检索和回答。新知识必须先进入测试 dataset 完成「彩排」，全部通过并完成线下审批后，才能复制到生产。

## 3. 知识来源与核心流程

### 3.1 数据源清单

| 类别 | 典型内容 | 是否进入索引 | 处理规则 |
|---|---|---|---|
| A 售后文档 | 保修政策、退换规则、安全处置 | 是 | 必须有负责人、版本与有效期 |
| B 商品文档 | 用户手册、参数表、协议说明 | 是 | 以商品中台为准，禁止手改 |
| C 结构化 FAQ | 标准问答、标准话术 | 是 | 答案必须关联权威来源 |
| D 渠道规则 | 天猫 / 京东 / 自营 / 抖音差异 | 是 | 按渠道分版本，不得混用 |
| E 合规文档 | 隐私与数据说明 | 是（P0） | 合规审核通过才能入库 |
| F 样本与实时数据 | 历史工单、订单、物流 | 否 | 工单脱敏后仅作评测样本；实时数据走业务 API |

**明确不进索引**：实时订单与物流、含个人信息的会话、未审核草稿、已过期政策、内部结算价。

### 3.2 端到端流程

| # | 阶段 | 主角色 | 输入 | 动作 | 产物 |
|---|---|---|---|---|---|
| 1 | 知识录入 | 知识运营 | 原文件 + 元数据 | 上传并保存草稿 | 草稿 + 版本记录 |
| 2 | 业务审核 | 业务审核人 | 待审文档 | 对比新旧版本，核对事实、范围、例外 | 审核结论 |
| 3 | 测试入库 | 知识运营 | 已审文档 | 推送测试 dataset | jobId |
| 4 | 处理验收 | 知识运营 | 回调结果 | 检查解析、切片、向量、索引一致性 | 验收结论 |
| 5 | 检索验证 | 知识运营 | 真实问题 | 看 Top K、相关度、来源、过滤原因 | 通过 / 问题案例 |
| 6 | 批量评测 | AI 产品经理 | 评测集 | 5 → 40 → 200 逐级跑 | 通过率与失败样本 |
| 7 | 发布 | 审批人 | 全部结论 | 线下审批 → 生产入库 → 冒烟 | 生产版本 |

### 3.3 状态机

| 状态 | 含义 | 进入条件 | 可执行动作 | 退出条件 |
|---|---|---|---|---|
| 草稿 | 录入修改中 | 新建 / 驳回 | 编辑、提交 | 必填完整 |
| 待审核 | 等待业务确认 | 提交 | 通过 / 驳回 | 结论明确 |
| 测试入库中 | 引擎加工 | 审核通过 | 查看进度、失败重试 | 回调完成或失败 |
| 待验收 | 加工完成 | 回调成功 | 验收 / 退回 | 三项检查通过 |
| 待评测 | 验收通过 | 验收 | 检索、评测 | 达到门槛 |
| 待发布 | 评测通过 | 全部达标 | 提交审批 | 审批通过 |
| 已发布 | 生产可用 | 生产入库 + 冒烟 | 下线、建新版本 | 新版本发布 / 下线 |
| 已下线 | 停止服务 | 过期 / 被替换 | 查看历史、重新送审 | 重新发布 |

### 3.4 数据质量与版本规则

- 每份正式知识必须有明确来源和负责人。
- 新版本不覆盖旧版本，历史可回溯、可回滚。
- 有效期到期前 30 天提醒负责人，到期自动退出检索。
- 同一文档同一渠道同时只能有一个生效版本。
- P0 知识（安全、隐私、退款）标注风险等级，双人审核。

### 3.5 冲突知识处理

1. 同文档新旧版本并存：以「生效中」为准，旧版永不进检索。
2. 品牌政策与渠道规则冲突：以渠道规则优先，审核阶段标注。
3. 同一事实写在多份文档：保留权威文档，其余改为引用，避免检索排序漂移。
4. 冲突未解决前，该场景禁止发布。

> 实测案例：鼓包处置同时写在《用户手册》与《安全规范》中，检索 Top1 命中手册（0.761）而非规范（0.738）。删除重复表述后排序恢复正常。

## 4. 与 FastGPT 的集成

### 4.1 集成原则

- 浏览器只访问企业后端（本地连接层），由后端携带密钥调用引擎。
- 平台保存业务版本与处理状态，引擎负责解析、切片、索引与生成。
- 适配层隔离：换引擎只改适配层，不改业务流程。

### 4.2 概念接口

| 接口 | 入参 | 出参 | 失败语义 |
|---|---|---|---|
| 提交加工 | 文档、业务标签、目标 dataset | jobId、collectionId | 参数错立即失败 |
| 查询任务 | jobId | 状态、进度、异常摘要 | 超时进入未知态 |
| 检索测试 | 问题、dataset、Top K、阈值 | 片段、相关度、来源 | 空结果区分「无知识」与「被过滤」 |
| 问答调用 | 问题、上下文、应用标识 | 答案 + 引用列表 | 无命中走兜底 |

### 4.3 环境隔离

| 环境 | dataset | 用途 | 准入 |
|---|---|---|---|
| 测试 | 测试库 | 内部检索与评测 | 审核通过即可推 |
| 生产 | 生产库 | 正式问答 | 评测达标 + 线下审批 |

### 4.4 失败与降级

| 场景 | 平台行为 | 应用侧表现 |
|---|---|---|
| 引擎不可用 | 暂停发布与调试 | 转人工并提示 |
| 检索超时 | 降级全文检索 | 变慢但仍可引用 |
| 无命中 | 返回兜底 + 人工入口 | 「暂时没查到，帮你转人工」 |
| 引用缺失 | 该条判定不通过 | 重新生成或判失败 |

## 5. 检索测试、评测与运营

### 5.1 检索调试

**验证什么**：用户这样提问时，系统有没有把正确的知识排进 Top K？

**怎么算通过**：运行真实问题，检查 Top 1/2/3、相关度与来源；正确则「确认通过」，否则「标记为问题」。

**当前配置**：语义检索 · 引用上限 3000 · 最低相关度 0.4 · 重排关闭（免费版限制）。

### 5.2 三阶段评测

| 阶段 | 样本 | 目的 | 通过标准 | 未达标处理 |
|---|---|---|---|---|
| 冒烟 | 5 | 核心链路 + P0 安全 | P0 失败 = 0 | 阻断 |
| 正式 | 40 | 主要问法与政策口径 | ≥ 90%，P0 全过 | 生成问题案例 |
| 全量回归 | 200 | 是否破坏原有能力 | ≥ 95%，无新增 P0 | 阻断发布 |
| 客服对话 | 5–10 轮 | 真实连续追问体验 | 人工判定 | 登记问题 |
| 生产冒烟 | 5 | 发布后核心链路 | 全部通过 | 立即回滚 |

### 5.3 问题案例与闭环

问题案例不是工单系统，而是「需要线下处理的问题证据清单」：保留来源、召回证据与版本快照，由相关团队线下修复后回到平台标记状态。同类问题再次发生则新建案例，不覆盖旧记录。

### 5.4 发布门槛

业务内容与 RAG 处理结果均已完成审核或验收；检索能命中正确知识；评测与对话验证达到门槛；回答可追溯到有效来源；未解决的高风险问题已清零。最终由企业按内部审批流程决定发布。

## 6. 验收与指标

### 6.1 验收标准

| 项 | 标准 |
|---|---|
| 知识库 | 20 份文档入库，7 类知识覆盖，解析无明显乱码 |
| 检索 | 20 条评测用例全部通过；回答带引用来源 |
| 流程 | 草稿 → 审核 → 验收 → 评测 → 发布全链路可在原型中走通 |
| 集成 | 原型经连接层调用引擎，密钥不出现在前端 |

### 6.2 指标定义

| 指标 | 分子 / 分母 | 目标 |
|---|---|---|
| 召回命中率 | 预期来源进入 Top K 的用例数 / 总数 | ≥ 90% |
| 引用可追溯率 | 回答引用有效知识版本的用例数 / 总数 | ≥ 95% |
| P0 通过率 | 未出现禁止内容的 P0 用例数 / P0 总数 | 100% |
| 兜底率 | 无知识时明确兜底的用例数 / 无知识用例数 | 100% |

### 6.3 待补数据

| 指标 | 现状 | 补法 |
|---|---|---|
| 单次查政策耗时 | 待补 | 抽样 20 通会话计时 |
| 口径不一致客诉量 | 待补 | 工单系统标签统计 |
| 隐私类回答不合规率 | 待补 | 抽检 50 条问答人工判定 |

## 7. 风险与非目标

### 7.1 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 同一事实多处存在 | 检索排序漂移，答错 | 权威文档唯一，其余改引用 |
| 切片拆散条件与例外 | 回答不完整 | 按段落切分 + 验收抽查 |
| 引擎版本升级不兼容 | 线上事故 | 适配层回归 + 灰度 |
| 免费额度耗尽 | 实验中断 | 控制样本量，先冒烟后回归 |

### 7.2 非目标

- 不做工单系统与复杂归因。
- 不做多模态（图片、语音）解析。
- 不做知识的自动生成与自动修复。
- 不做多租户自助开通与计费。
